# 진단 응답의 날짜별 기록과 분석 차단 — 2026-10-16

## 사용자 흐름

- 새 건강정보와 기존 내역의 ‘다시 기록’은 이용확인부터 시작한다. 이용확인을 완료하기 전에는 건강정보·분석 단계로 건너뛸 수 없다.
- 당뇨병 진단 여부를 ‘예’로 선택하면 건강정보 입력·분석 탭을 즉시 비활성화한다. 저장 후 별도 ‘당뇨병 진단’ 내역을 남긴다. 기존 건강정보에서 다시 기록할 때는 원래 건강정보 ID와 날짜에 연결하며, 일반 신규 응답은 오늘(Asia/Seoul)에 저장한다. 의료진이 확인한 실제 진단일로 추정하지 않는다.
- 의료 안내에서 “진단 기록 내역 보기”를 눌러 건강정보 관리의 저장 내역으로 이동할 수 있다.
- 진단 내역에는 예측·분석 비활성화 안내를 표시하며, 같은 날짜의 기존 건강정보에서도 분석 결과 버튼을 비활성화한다.
- 진단 내역에도 ‘다시 기록’과 ‘기록 삭제’를 제공한다. 잘못 입력했다면 해당 내역에서 다시 기록해 ‘아니요’로 저장하거나 삭제 확인 후 제거한다. 건강정보·분석 원본과 이용확인 응답 이력은 보존한다. 정정·삭제한 내역은 새로고침·서버 재시작 후 부활하지 않는다.
- 건강정보와 연결된 진단은 원래 날짜를 유지한다. 건강정보 없이 만들어진 기존 진단 내역은 다시 기록에서 날짜도 수정할 수 있다. 미래 날짜 및 다른 활성 진단이 있는 날짜로의 이동은 거절한다.
- 다른 날짜의 기록은 계속 보관한다. 일반 신규 이용확인의 ‘아니요’ 응답으로 기존 진단 내역을 자동으로 제거하지 않으며, 해당 내역의 수정·삭제로 처리한다. 새 기록은 다시 이용확인을 거친다.

## 저장과 API

HealthDiagnosisRecord(health_diagnosis_records)에 계정·날짜별 활성 진단, 연결 건강정보 ID, 이용확인 응답 ID 목록을 저장한다. EligibilityCheck는 감사 목적으로 보존한다. 가짜 신체 수치·건강정보는 생성하지 않는다. 마이그레이션 28_20261016090000_editable_diagnosis_records.py가 별도 테이블을 추가한다. 로컬 DEMO 서버는 시작 시 테이블 생성 후 기존 ‘예’ 응답을 Asia/Seoul 날짜로 가져온다. 처리한 응답 ID는 삭제·정정 후에도 보존하여 재시작 시 내역을 다시 만들지 않는다. 운영 환경에 적용하려면 별도 마이그레이션과 기존 응답 가져오기 작업이 필요하다.

- POST /api/v1/eligibility-checks: 선택 입력 health_checkup_id, diagnosis_record_id, record_date로 수정 대상을 명시한다. 소유권·원래 날짜를 검증하고 응답 저장과 진단 갱신을 한 트랜잭션으로 처리한다. 문맥 없는 과거 날짜 입력은 거절한다. record_date, analysis_blocked_for_date, diagnosis_record를 반환한다.
- GET /api/v1/diagnosis-records: 로그인 계정의 별도 진단 내역.
- DELETE /api/v1/diagnosis-records/{record_id}: 본인의 활성 진단을 삭제 처리한다. 다른 계정·없는 내역은 404다.
- GET /api/v1/health-checkups: 기존 items에 diagnosis_records 추가. 건강정보 항목에는 analysis_allowed, prediction_allowed, analysis_block_reason을 포함.
- 진단 기록일의 신규 건강정보 생성·수정, 오늘이 보조 정보 저장, 모델 작업 생성, 저장된 예측·SHAP·위험곡선 개별 조회는 403으로 차단.
- 예측 목록·변화·대시보드는 해당 날짜의 결과를 제외한다. 기존 분석 데이터 자체는 삭제하지 않는다.
- 권한 오류 코드: DIABETES_DIAGNOSIS_RECORDED.
- 기존 의료 안내 및 진행·예약 4주 챌린지 종료 정책은 유지한다. 긴급 증상과 진단을 함께 응답해도 진단을 저장하며 긴급 안내가 우선한다.
