# 로컬 음식 사진 CV·VLM 보완 적용

## 활성화와 실행

- 적용 저장소: `local-develop`, 로컬 API `http://127.0.0.1:8000`.
- 로컬 설정의 `OPENAI_VLM_FALLBACK_ENABLED=true`, 모델 `gpt-4o-mini`.
- `OPENAI_API_KEY_FILE`은 로컬 키 파일 경로만 저장한다. 실행기가 키를 읽어 서버 프로세스의 `OPENAI_API_KEY`에 주입한다. 키 값은 저장소·로그·프런트엔드·테스트 결과에 기록하지 않는다.
- 실행 시 이미 `OPENAI_API_KEY`가 설정돼 있으면 파일보다 우선한다. 활성화 상태에서 키가 없거나 파일에 여러 키가 있으면 실행을 중단한다.
- 키 파일 경로·설정 변경 뒤 `scripts/stop-local-mobile.ps1`, `scripts/start-local-mobile.ps1`로 로컬 서버를 재시작한다. 설정 파일과 원본 사진은 Git에서 제외된다.
- 2026-10-09 공개 시연 사진의 실제 OpenAI Responses 요청 성공: `local_kfood_openai_vlm`, `needs_confirmation`. 서버 `/api/v1/ready`의 VLM enabled/ready 모두 true. Ready는 구성 확인이며 실제 연결 성공은 별도 요청 결과로 확인했다.

## 인증 흐름

1. 채소 사진 화면에서 김치, 채소를 덮는 진한 양념/소스, 흰 음식과 흰 식기/배경을 각각 `있음/없음/잘 모르겠음`으로 입력한다. 기본값은 `잘 모르겠음`이다.
2. 서버는 파일 형식·크기·화소를 검사하고 JPEG로 변환해 EXIF와 위치정보를 제거한다.
3. TFLite 픽셀 분할기로 두 면적만 계산한다. **음식 픽셀 / 사진 전체 픽셀 ≥ 50%, 채소 픽셀 / 음식 픽셀 ≥ 30%**다. V3 인증은 EfficientNet 음식명 분류를 실행하지 않고 음식명에 따른 신뢰도 보류도 적용하지 않는다. 분할기가 음식/채소 영역을 불확실하게 처리하는 경우의 안전장치는 유지한다.
4. CV가 불확실하거나 기준 근처이거나 사용자 체크 중 하나라도 `yes/unsure`이면 VLM을 호출한다. 모두 `no`여도 CV가 불확실하면 보완한다. 예전 클라이언트가 필드를 보내지 않으면 기존 CV 조건으로 보완한다.
5. VLM은 식사 관련성, 채소 유무(`present/absent/uncertain`), 사진 품질, 음식/배경과 채소/다른 음식의 경계, 화면 캡처 여부를 각각 검토한다. 세부 음식명을 요청하지 않는다. `food-photo-v2` 지침은 한 접시 음식도 사진 검토 대상으로 정의하고, 김치가 채소로 식별되는지와 경계가 명확한지를 분리한다. 사용자 체크는 정답으로 취급하지 않는다. VLM은 면적·중량·영양소·실제 섭취·혈당이나 치료 효과를 추정하지 않는다.
6. **CV의 면적 기준과 신뢰도가 모두 충족되고 VLM 검토도 명확한 경우에만** `needs_confirmation`으로 진행한다. 사용자가 같은 사진·같은 체크 답변으로 최종 확인해야 `accepted`와 완료 기록이 저장된다.
7. CV 면적이 미달하거나 분할이 불확실한데 VLM은 채소를 확인했다면 `needs_review`로 보류한다. VLM이 채소가 보인다고 면적 기준을 대신 충족시키지 않는다. 경계·품질 불명확, 결과 충돌, API 오류도 보류한다. 채소가 확실히 없으면 `invalid_vegetable_content`, 음식 사진이 아니거나 화면 캡처로 판정되면 `invalid_photo_content`로 거절한다. 의미 기반 거절은 픽셀 비율 미달과 구분해 안내한다.

최종 확인의 사진 해시는 체크 답변도 포함한다. 답변을 바꾸면 새 검토 초안이 필요하다. 동일 날짜의 이미 완료된 기록은 중복 저장하거나 보상을 추가 지급하지 않는다. 활동 사진은 음식 체크와 VLM 흐름을 사용하지 않는다.

## 보완 범위와 한계

VLM은 김치·양념 채소의 존재 확인과 흰 음식/흰 식기의 경계 문제를 감지하는 보완 장치다. **분할 마스크를 수정하거나 새 면적을 계산하는 모델은 아니다.** 음식명에 따른 보류는 인증에서 제거했지만, 픽셀 분할 자체가 불확실하면 VLM만으로 면적을 보증하지 않는다. 사진을 다시 찍어도 지속되는 면적 오류는 별도의 분할 모델 개선과 정답 마스크 검증이 필요하다.

사용자 체크를 끄거나 `없음`으로 답했다고 기준을 낮추지 않으며, 체크 내용 자체로 통과하지 않는다. 외부 검토에 보내는 것은 정제한 사진과 세 개의 체크 답변이다. 이름·계정·건강 측정값·원본 파일명·EXIF는 보내지 않는다. OpenAI 요청은 `store=false`와 엄격한 JSON Schema를 사용한다.

## 검증

- CV 면적 판정, 인증 API, 키 파일 로딩, Responses 응답 계약 회귀 테스트: 124개 통과. 분류기 미실행, 잘못된 타입·채소 상태 불일치·미완료 응답의 보류도 검증했다.
- 사진 프런트엔드 테스트: 14개 통과. 모바일 패키징·통신 테스트: 15개 통과.
- 경계값 미달·잘못된 수치·CV 불확실성·VLM 불명확/실패는 자동 완료되지 않음을 확인했다.
- 같은 사진에서 체크 답변을 바꾸면 이전 확인 초안을 사용할 수 없으며, 정상 최종 확인 후에도 완료 기록은 한 개임을 확인했다.
- 390·720·1280px 오류 안내, 취약 조건 입력·보류 화면 검증 통과. `scripts/mobile/check-vlm-photo-flow.mjs`로 재현한다.
- BlueStacks의 로컬 앱 `life.dangno.app`에 갱신한 웹 화면을 설치하고, 실제 WebView에서 세 입력의 존재·초깃값 `unsure`와 CV/VLM enabled/ready를 확인했다. 기존 네이티브 APK의 웹 자산만 갱신했으며, 서명과 Android 정렬을 검증한 업데이트 설치로 앱 데이터를 유지했다. 전체 Gradle 재빌드는 수행하지 않았다. 설치본·복원용 원본·읽기 전용 확인 결과는 `outputs/mobile/vlm-photo-flow/`에 보관한다.
- 배포 앱 점검 이후 로컬 버전을 다시 열어 `/api/v1/ready` 200, 새 체크 입력 3개가 있는 OpenAPI와 실제 앱의 CV/VLM ready를 재확인했다. 공개 사진 2장으로 로컬 서버와 같은 `_review`를 실행한 실제 OpenAI 요청도 성공했다. 김치 표본은 음식 51.79%·채소 99.47%로 `needs_confirmation`, 밥 표본은 CV 음식 64.10%·채소 73.32%였으나 VLM의 채소 없음 검토로 `rejected`였다. 음식명 분류를 실행하지 않는 면적 중심 경로를 확인했고 사용자 DB에는 완료·보상을 쓰지 않았다. 기록은 `outputs/mobile/vlm-local-check-20261009/real-review.json`이다.
- 사용자 요청에 따라 무선 ADB로 연결된 실제 휴대폰(SM-S931N)의 로컬 앱에도 반영했다. 설치된 APK를 보관하고 같은 서명을 확인한 뒤 음식 사진 웹 파일 7개만 갱신한 APK를 일반 사용자 프로필 0에 데이터 유지 설치했다. 네이티브 코드·로컬 API 런타임은 유지했고 전체 Gradle 재빌드는 하지 않았다. `reverse tcp:8000 tcp:8000` 연결 후 실제 휴대폰 WebView에서 세 입력·기본값 `unsure`, API 주소 `http://127.0.0.1:8000`, 준비 상태 200과 CV/VLM ready를 확인했다. 이 휴대폰 점검은 읽기 전용으로 수행했고 사용자 사진 제출·완료·보상 기록을 만들지 않았다. APK·체크섬·복원본·검증 결과는 `outputs/mobile/vlm-wireless-20261009/`에 있다.

## 공개 사진 비교 실험

수집기: `scripts/collect-food-photo-benchmark.py`. 평가기: `src/ml/evaluation/food_photo_benchmark.py`.

- 공개 [한식 이미지 데이터](https://huggingface.co/datasets/Jiho0o0/kfood_image_englabel)와 [MM-Food-100K](https://huggingface.co/datasets/Humanbased-AI/MM-Food-100K)에서 김치와 조리된 밥을 각 100장 선택한다.
- 난수 시드 `20261009`, 출처 행·데이터셋 revision·이미지 SHA256·해상도를 저장한다. 최소 변 128px, 정제 JPEG 최대 1600px. 원본 의료 데이터와 사용자 사진을 사용하지 않는다.
- 픽셀 중복 및 dHash 거리 3 이하의 유사 사진을 제외한다. 육안 점검에서 생쌀로 보인 밥 라벨 표본도 제외한다. 수집 데이터·사진·결과는 `outputs/food_photo_benchmark_20261009/`에만 저장한다.
- 실제 CV와 VLM 요청을 실행하며, CV 숫자는 고정한 채 사용자 체크를 포함한 보완 검토 결과를 비교한다. 동시 OpenAI 요청은 기본 3개다. 분류 제외 후에는 같은 사진·같은 지침의 VLM 응답을 재사용하고 면적 CV만 다시 실행한다. 실제 사용자 챌린지 DB에는 기록하지 않는다.
- 음식 이름 라벨은 정확한 면적 마스크나 인증 정답이 아니다. 이 실험의 통과/보류 비율을 모델 정확도라고 해석하지 않는다. 분할 정답 마스크가 없으므로 실제 면적 오차는 계산하지 못한다. 최초 VLM 지침의 과도한 보류를 발견해 지침을 개선한 진단 실험이며, 독립적인 최종 성능 검증으로 간주하지 않는다. 면적 임계값과 모델 가중치는 변경하지 않았다.

## 배포 버전 앱 반영 (2026-10-09)

- BlueStacks의 `간당간당(배포)`(`life.dangno.app.deployment`)에 음식 사진 관련 HTML/JS/CSS 7개 파일을 업데이트 설치했다. 기존 APK와 브랜치 기준본이 일치함을 확인하고 이번 사진 체크 변경만 반영했다. 원래의 HTTPS API 주소 `https://www.dang-no.life`, 네이티브 코드와 앱 데이터는 유지했다. 서명·APK CRC·Android 정렬을 검증했으며 모바일 테스트 15개가 통과했다.
- APK는 `outputs/mobile/vlm-deployment-20261009/gandang-deployment-food-vlm.apk`, 체크섬은 같은 폴더의 `MANIFEST.json`, 복원용 기존 설치 APK는 `installed-deployment-before.apk`다. 전체 Gradle 재빌드는 수행하지 않았다.
- 공개 서버 조회에서 `/health`는 200, `/api/v1/ready`는 503이었다. VLM enabled/ready는 true이나 CV ready는 false였다. 현재 공개 OpenAPI에는 `contains_kimchi`, `strong_seasoning`, `white_food_on_white` 입력도 없다. **앱 화면 반영은 완료했지만 서버의 면적 중심 CV·VLM 코드 반영과 CV 런타임 복구는 아직 완료되지 않았다.** 서버 접속 정보가 필요하다.
- 서버 반영용 코드·테스트·문서는 `server-food-vlm-source.zip`, 확인할 절차는 같은 폴더의 `SERVER_HANDOFF.md`로 준비했다. 키·모델·사진·DB는 묶음에 포함하지 않는다.
- 사전 저장 동의로 분석 뒤 최종 확인을 제거하는 흐름은 제안 단계다. 이번 앱에도 현재 구현한 분석 후 최종 확인을 유지한다.

### 픽셀 계산 구조

분할기는 513×513 RGB 입력을 26개 픽셀 클래스로 분할한다. 각 픽셀에서 최대값인 클래스 하나를 선택하며, 배경/기타 `[0, 23, 24]`를 제외한 픽셀을 음식 면적으로 본다. 채소 픽셀은 `[1, 2, 3, 4]`이고 전분성 식재료 클래스 `14`는 채소 비율에서 제외한다. 채소 픽셀 수는 음식 픽셀 안에서만 센다. 음식 픽셀이 0개면 채소 비율은 0이다.

면적 검증을 더 개선하려면 흰 음식/식기의 경계와 양념 채소를 포함한 **정답 픽셀 마스크**를 만들고 음식·채소 영역의 오차를 검증해야 한다. 세부 음식명 분류 정확도를 높이는 것은 현재 인증 목표의 필수 조건이 아니다.
